# CfC 分层决策中枢 · 设计文档

> 目标：让机器人上的 CfC 不只输出「转头 / 转身 / 前进」，还输出**「这件事我自己能不能处理，处理不了该交给谁」**，
> 并且让这个判断在本地、在毫秒级完成。
>
> 代码：`hub.py`（路由器）、`llm_backend.py`（上下行契约 + 真/mock 后端）、
> `local_agent.py`（真实 L2：调 `../agent_bridge/server.py`）、`demo.py`、`demo_real.py`、
> `test_hub.py`、`test_real_backend.py`、`FIRMWARE_CHANGES.md`

---

## 0. 结论先行

1. **升级判据是一个 13 参数的广义可加模型**（12 个有名字的风险势函数 + 1 个偏置），
   `p_esc = σ(b + Σ wₖφₖ)`。不是 if 堆，也不是黑箱 MLP：
   logit **精确等于**各势函数贡献之和，所以「为什么升级」是算出来的，不是编出来的。
2. **层级不是按「难不难」选，而是按「缺的是什么资源」选**：`P_fix(L) = softmax(b_L + Σ W_Lkφₖ)`，
   再和代价一起做决策论最优化：`U(L) = p_esc·P_fix(L) − C_L`，只在 `max U > 0` 时升级。
   阈值不是拍的，是代价比的解。
3. **L0 永不等待**。升级请求发出去的同一个 tick，机器人仍在按 50Hz 出可执行指令
   （等待期策略：车轮清零、头继续跟人、脸上挂「在想」）。
4. 实测：L0 决策链 **38~64µs（热循环，随机器负载波动）/ ~115µs（50Hz 实时循环内，多次运行 115~120µs）**，
   L2 真实 HTTP 往返 **1.2~16ms（p50，随主机负载波动）**，L3 往返 **740~860ms**，
   到 DeepSeek 的真实 TLS+HTTP 下界 **165ms**（无 key 探测，HTTP 401）。
5. 验收：`python test_hub.py` **90/90 PASS**（~9s）；`python test_real_backend.py` **58/58 PASS**
   （~11s，真的拉起 `agent_bridge` 子进程）；`python demo_real.py` **3/3 真实执行**（detail 经独立核对）；
   `python demo.py` **8/8 场景按预期分层**。

## 1. 问题：为什么「要不要升级」必须本地做

参考生物学的分层反射弧：

| 层 | 生物对应 | 延迟量级 | 本系统 |
|---|---|---|---|
| L0 | 脊髓反射 | 几十 ms | 机器人本地 CfC，50Hz，直接驱动 LQR |
| L1 | 脊髓中间神经元 / 小脑 | 上百 ms | 机器人自身的动作原语程序（本地播放） |
| L2 | 皮层 | 几百 ms | PC 上的 agent（有帧、有算力、有工具） |
| L3 | 前额叶 + 语言 | 秒级 | 云端 LLM（ASR、开放域、外部工具） |

**关键洞察**：负责「这件事我处理不了」的判断，和负责「转过头」的判断，必须是同一层、同一时钟。
因为一旦把升级判据放到云端，链路就变成「我处理不了 → 问云端我能不能处理 → 云端说处理不了」，
两跳 RTT 之后黄花菜都凉了（实测到云端 TLS+HTTP 单次往返 165ms，加上模型推理 1s 起）。

推论：**升级决策必须是一个本地前向计算**，成本和 CfC 的一个 head 相当。
本文的所有设计都是为了满足这条约束——它排除了「调用云端做不确定性估计」这类看起来更聪明的方案。

## 2. 分层结构：按「缺什么资源」而不是「有多难」

朴素的「按难度分层」会退化成一个魔数阈值。这里改成问：**当前这一刻，本地缺的到底是哪种资源？**

| 缺失的资源 | 表现 | 该由谁修 |
|---|---|---|
| 不需要（本地够用） | 跟踪正常、动作置信度高 | L0 |
| 注意力 / 视角 | 看不见、目标丢了、特征域外（但**没有信息可取**） | L1（本地扫描、重捕获、摆姿态） |
| 一块看得更清楚的算力 | 有画面但看不懂（指着什么？什么新奇东西？） | L2（PC 有帧、有更大的模型） |
| 语言与世界知识 | 人在说话、要多步规划、要查资料 | L3 |

这个视角的价值在于：**它让「层级选择」可以被学习，而且学的是可观测的东西**。
`P_fix(L)` 就是「这一级能把这件事修好的概率」，训练标签是「事后看，哪一级真的修好了」——
一个有明确定义、可采样的量，而不是「专家觉得这题难」。

## 3. 升级判据（核心）

### 3.1 要预测的两个量

- `p_esc`：**这件事本地处理不了的概率**（二分类，一个 sigmoid）。
- `P_fix(L)`：**给定要升级，第 L 级能修好的概率**（三级 softmax）。

分开建模的好处：门控只需要「该不该求助」，路由只需要「找谁」；
两者的标签来源不同、采样难度不同，混成一个 4 类 softmax 会把两件事的置信度搅在一起。

### 3.2 候选形式与取舍

| 形式 | 可解释 | 可训练 | 数据需求 | 判断 |
|---|---|---|---|---|
| 一组 if 阈值 | ✅（人能读） | ❌ 不可导，梯度为零 | 0 | **否决**：无法校准、无法用数据改进、处处抖动 |
| MLP on CfC hidden (64→64→1) | ❌ 无法归因 | ✅ | 10³~10⁴ 条标注 | **否决**：升级是稀有事件，标注拿不到；且无法向用户解释「你刚才为什么把画面传上云了」 |
| **可加记分卡（采用）** | ✅ 精确分解 | ✅ 凸（13 参数） | 10² 条量级 | ✅ 兼顾，且能直接部署成 50 MAC |

表格里第三行就是最终选择：

```
z     = b + Σₖ wₖ·φₖ(obs)                     # φ 是 12 个风险势函数
p_esc = σ(z)
```

为什么这是「可训练」的而不是「一堆手调阈值」：
- 每个 φₖ 都是 **C¹ 平滑**的（`smoothstep`），不是阶跃——硬阈值处处导数为 0，梯度流不回去，那才是真的不可训练。
- 权重和偏置只有 13 个，`fit_gate()` 解的是一个**凸**问题（逻辑回归），
  2500 条样本 500 轮就收敛，不依赖初始化（见 `test_hub.py::test_trainable`：注入 3 个已知权重，能学回来，无关权重被压到 0.21 以下）。
- 时间维度不靠黑箱记忆，而靠**显式的泄漏积分器**（对离散检测量做 `ema_tau` 一阶平滑），
  这既保留了「持续 3 秒有人在说话」这种时间证据，又保持可解释（每个 φ 本身仍然是可读的量）。

### 3.3 十二个风险势函数

全部取值 ∈ [0,1]，全部有量纲、有方向、有物理解释。`φ=0` 表示「没有这类风险」，`φ=1` 表示「这类风险已经拉满」。

| # | 势函数 | 族 | 权重 w | 路由 L1/L2/L3 | 含义与公式 |
|---|---|---|---|---|---|
| 1 | `u_conf` | blind | +4.2 | +3.0/−1.0/−2.0 | 置信度不足：`smoothstep(person_conf; 0.55→0.15)`（反向） |
| 2 | `u_lost` | blind | +4.6 | +2.6/−1.0/−2.0 | 目标丢失：`seen=0` 时 `smoothstep(age_ms; 250→1200)` |
| 3 | `u_clip` | unknown | +3.0 | +0.2/+1.2/−0.4 | 特征出域：`smoothstep(clip_ratio; 0.15→0.50)`（0.5 与 §7.5 对齐） |
| 4 | `u_ood` | unknown | +3.6 | +0.2/+1.8/+0.4 | 场景不在训练分布：`smoothstep(novelty; 2.5σ→5.0σ)` |
| 5 | `m_speech` | language | +5.0 | −0.8/+0.4/+2.2 | 人在说话（0/1，带 0.15s 平滑）。本地没有 ASR |
| 6 | `m_point` | language | +4.4 | −1.0/+1.6/+0.4 | 指着/举着东西 `max(pointing, object_held)`。需要物体识别与指代消解 |
| 7 | `m_stale_sem` | context | +2.0 | +1.6/−0.8/−1.6 | 语义通道过期 `smoothstep(sem_age; 400→1500)`。**注意它路由到 L1** |
| 8 | `p_multi` | planning | +5.2 | −0.6/−0.4/+2.4 | 一句话多个动作 `smoothstep(clauses; 1→3)` |
| 9 | `p_lookup` | planning | +4.8 | −1.6/−0.8/+2.8 | 需要查资料 / 外部工具（0/1） |
| 10 | `s_irrev` | stakes | +2.6 | +0.2/+1.4/+0.8 | `(1−action_conf)·smoothstep(|a|/a_max; 0.25→0.90)`：动作大且没把握 |
| 11 | `s_approach` | stakes | +3.2 | +0.4/+1.2/+0.6 | `(1−action_conf)·smoothstep(vx; 0.03→0.15)·smoothstep(1.1−dist; 0→0.6)`：要不要靠近 |
| 12 | `c_local_ok` | context | −1.0 | 0/0/0 | **反证项**：`seen·smoothstep(conf; 0.60→0.85)·(1−max(其它语义风险))` |

偏置 `b = −3.0`。

关于权重必须先说清楚的一件事：**这 12 个权重目前是先验，不是训练结果**（没有标注数据）。
但先验不是拍脑袋的，见 §3.4 的推导。接口留好了：`fit_gate()` / `fit_router()`。

几个设计要点：

- **第 10、11 项是显式写出来的交互项**。可加模型本来表达不了「置信度 × 影响」这种乘积，
  但这里的两类风险（没把握 / 影响大）都有明确的物理解释，直接把乘积算成 φ 是合理的，
  也让「没把握但选了个大动作」这件事在解释里一眼看得见。
- **第 12 项是负权重的反证项**。没有它，五个中庸的风险（各 0.3）相加就会误触发。
  它在「本地确实看得很清楚且没有任何外部语义需求」时把基率压回去。
- **第 7 项故意路由到 L1**。「我不知道他刚才是不是在说话」不能靠问云端解决——
  云端的语义通道和本地是同一路，过期了就是过期了；正确的反应是本地摆出「请再说一遍」。
  这一条是「按缺什么资源分层」这个原则最直接的体现。
- **安全否决不进判据**。桌沿危险 / 摔倒 / 视觉彻底丢失这三种情况不走学习模型，
  直接 `level=0` + `veto`，见 §3.5 末尾。理由：安全是规格，不是概率。

### 3.4 权重先验怎么来的

不是拍脑袋，是从「代价比」反推的量级约束。以 L2 为例：

```
升级到 L2 的代价      C₂ = 0.12  （单位：一次任务成功 = 1；含义见下）
不升级而失败的机会成本  V  = 1
贝叶斯阈值            τ₂ = C₂ / (C₂ + V) = 0.107
```

也就是说：**只要「本地处理不了」的概率超过 10.7%，问一次 PC agent 就是划算的。**
（这是二分类的经典结果：当 `p·V > (1−p)·C` 时行动。阈值随层级代价不同而不同，
L1 便宜到 τ₁=0.048，L3 贵到 τ₃=0.259——注意 router 的偏置已经把「贵的层要更确定」这件事编码进去了。）

于是每个权重只需满足一个可检验的约束：**该势函数单独拉满时，必须跨过它该去的那个层级的阈值**。
例如 `m_speech = 1`：`z = −3.0 + 5.0 = 2.0 → p_esc = 0.88`，
再乘上 `P_fix(L3) ≈ 0.76`，`U(L3) = 0.88×0.76 − 0.35 = +0.32 > 0` ✅ 会升级。
而 `m_stale_sem = 1`：`z = −3 + 2.0 = −1.0 → p_esc = 0.27 → U(L1) = 0.27×0.66 − 0.05 = +0.13`，
只在 L1 上成立，L3 上是 `0.27×0.07 − 0.35 < 0` ✅ 不会去打扰云端。

层级代价 `C_L` 的取值依据（这是唯一需要人来定的部分，也只需人来定）：

| 层 | C | 依据 |
|---|---|---|
| L1 | 0.05 | 打断跟踪约 0.3~1.2s，有跟丢人的风险，但完全本地、无副作用 |
| L2 | 0.12 | 一次 WiFi 往返 + PC 算力 + 0.1~0.3s 延迟；不含钱 |
| L3 | 0.35 | 1s 量级延迟（人已经走开了）+ token 成本 + 把画面/音频传出去的隐私代价 |

**这三个数是策略旋钮，不是物理常数**：部署在纯内网、由用户自己的模型提供服务时，把 `C₃` 调小就自动变得更爱用云端。

### 3.5 从概率到层级：决策论，不是阈值

```python
P_fix(L) = softmax_L(b_L + Σₖ W_Lk·φₖ)        # 哪一级真能修好
U(L)     = p_esc · P_fix(L) − C_L             # 期望收益
level    = argmax_L U(L)，且仅当 max U > 0     # 否则留在 L0
```

两个经常被忽略但很关键的处理：

**(a) `P_fix` 要在「当前可用的层级」里重新归一化。**
云端挂了，`P_fix(L3)` 这个概率就不该再参与竞争。重新归一化之后，
「大模型全挂 → L1 的条件概率 = 1 → 去做点力所能及的」是**同一个公式的推论**，
而不是一个特判分支。`test_hub.py` 里有专门的断言（`P_fix(L1) == 1.0000`）。

**(b) 失败后的降级是「重新挑一次」，不是「无脑降一级」。**
L3 超时后，用**发起时算好的** `U(L2)` 再判断一次：划算就转 L2，不划算就直接落 L1。
（`demo.py` 的 S5 走的就是 L3 超时 → L2 接住；因为那次「一句话一个动作」，
L2 的 `P_fix=0.29` 让 `U(L2)=+0.10 > 0`。）

**(c) 安全否决绕过整个模型。** `robot_state=0`（摔倒/被抱起）、`gaze_danger=1`（桌沿）、
`feat_age > lost_ms`（视觉彻底没了）→ 直接 L0 + `veto` 原因。
理由：安全是规格要求，不应该被一个概率乘数削弱。此时升级也没有意义——没有信号可以问。

### 3.6 可解释性：一行判据就是一次精确归因

因为 `z = b + Σ wₖφₖ`，每个样本的贡献可以**精确拆开**，不需要 Shapley 采样：

```
判据 m_speech=1.00(+5.00) p_multi=0.50(+2.60) u_conf=0.00(+0.00) ...
风险族 language（决定本地技能与路由方向）U(L)=L1:-0.04 L2:-0.01 L3:+0.48
```

- 「为什么升级」= 贡献绝对值排序的前几项。`test_hub.py` 断言 `logit == b + Σ贡献`（误差 1e-9）。
- 「为什么是 L3 不是 L2」= `P_fix` 与 `U(L)` 的直接对比。
- 每次升级都把这些写进上行 JSON（`why` / `phi` / `p_esc` / `level`），
  日志里可以离线复算任何一次决策，包括抽样复核「这次升级是不是多余的」。

**这对机器人是刚需，不是学术洁癖**：一个会说不出理由的机器人，用户不会让它把摄像头画面传到云端。

### 3.7 可训练性：标签从哪来

三个来源，按成本排序：

1. **事后标注（hindsight）**，主要来源。跑一遍本地策略，记录每一步的 `φ`；
   用「N 步之后的结果有没有达成意图」来标注：本地做完之后任务失败/退化的片段 → `label=1`。
   这是「结果导向」的标签，不需要人。
2. **教师控制器的显式标记**。现有 `pc/teacher/teacher.py` 的规则层已经知道
   「这一帧属于哪种模式」；把「规则层需要外部信息才能继续」的时刻标出来即可。
3. **人在环**。用户点一次「刚才问我不就完了」，就是一条高价值正样本。

训练本身：

```python
w, b, info = fit_gate(samples)      # 凸问题，2500 样本 500 轮 ~0.5s
rw, rb, info = fit_router(samples)  # 「事后看哪一级真修好了」
```

必须做的两件事：
- **校准**。`p_esc` 只有在标定过之后才有「概率」的含义。上线前用一片 hold-out 做温度标定
  （一个标量 `T`，`z/T`），否则 §3.4 的阈值推导就是空中楼阁。
- **监测各族的触发率**。如果 `m_stale_sem` 占升级原因的 80%，那不是判据好坏的问题，
  是 PC 侧语义通道的健康问题——判据的贡献分布本身就是一条运维指标。

### 3.8 我们放弃了什么

可加模型的表达力上限是明确的：**学不到高阶交互**（例如「只有当人在说话 **且** 场景新奇时，
才该升级到 L3 而不是 L2」这种三阶关系）。

三种缓解，按代价排序：
1. 显式写出交互项（本设计已经在 `s_irrev` / `s_approach` 上这么做了）；
2. 用泄漏积分器把时间维度变成势函数自己的状态（本设计已经做了）；
3. 加一个**有界残差**：`z = z_scorecard + tanh(u·h)`，其中 `h` 是 CfC 隐状态、`u` 是一个学习到的投影。
   `tanh` 把残差的 logit 幅度限制在 ±1 以内 —— 也就是说黑箱最多能把概率挪 0.27，
   永远盖不过可解释部分。这样既留了容量，又不会让「原因」被残差吃掉。
   当前实现里 `u=0`（未训练），接口位置已经留好（固件侧对应一个 `head_act=tanh` 的头，见 FIRMWARE_CHANGES §4）。

| L3 | cloud 往返（含建模思考 850ms） | 740.1ms | 848.2ms | 860.2ms | 2 | **实测**（真线程 + 真 JSON） |
| L3 | 云端 TLS+HTTP 传输下界（无 key 探测，HTTP 401） | 165ms | — | — | 1 | **实测**（真实网络，到 api.deepseek.com） |

怎么读这张表：

- **38~64µs 和 ~115µs 差 2~3 倍**，这不是算法问题：实时循环里每 20ms 才跑一次，
  CPU 处于低功耗状态，每拍都要付缓存冷启动 + 唤醒的开销。热循环测的是纯算法成本。
  两个数都真实，用途不同——做机器人算力预算要按前者，做算法优化要按后者。
- **L0 的热循环耗时里，`decide()` 约 15µs、`_sanitize_obs()` 约 12µs、`compute_phi()` 约 5.5µs、其余是动作构造。**
  在 ESP32 上这一整套是 12 个乘加 + 12 段三次多项式 + 一次 exp，
  按 240MHz 保守估 ~150 周期 ≈ **1.2µs**，相对 20ms 的推理周期可以忽略。
- **L1 的 1.26s 是程序时长不是延迟**。发出指令到第一个动作是**同一个 tick**（本地播放，0 网络）。
- **两个 L2 行要分开看**：`mock` 那行的 99.8ms 里 85ms 是 sleep 出来的建模思考时间；
  `真实` 那行是 agent_bridge 真的在主机上执行了一次动作（`clock`/`disk`/`note`/
  `system_status`），不含任何 sleep，波动来自主机调度（同一台机器不同时段能差 10 倍）。
  L3 的 850ms 仍是建模值，表里**纯粹来自真实网络**的仍然只有那 165ms 和下界。
- **L3 不能进 50Hz 环**，也不该进任何同步路径。它的唯一合法用法是「异步派发 + 本地继续跑反射」。

## 5. 降级与回退

状态机（`DecisionHub.state`）：

```
        ┌────────── p_esc > 门限 且 驻留够 且 按层级加锁 ──────────┐
        │                                                        ▼
     IDLE ──────────────────────────────────────────────────► WAIT (派发 L2/L3)
        ▲                                                        │
        │  程序播完 / 冷却到点                                      │ 成功：拿到并校验指令
        │                                                        ▼
   COOLDOWN ◄──────────── EXEC（本地按 50Hz 播放动作程序）◄──────┘
        │                        ▲
        │                        │ 全部失败：L1 兜底技能
        └────────────────────────┴────────── _step_down()
```

逐条规则：

| 情形 | 行为 | 是否阻塞 L0 |
|---|---|---|
| 等待上层 | 车轮清零、机身不转、**头继续跟人**、表情「在想」 | 否 |
| 上层超时（`ttl_ms`） | 记录超时，按 `U(L)` 降一级；都不可行则落 L1 | 否 |
| 上层返回非法 JSON | 整条丢弃（`InvalidInstruction`），降一级 | 否 |
| 返回的 `id` 对不上（迟到回复） | 丢弃，计数 `stale_reply`，降一级 | 否 |
| 后端抛异常 | 记 `failures`，降一级 | 否 |
| 后端 `available()=False` | 该级根本不出现在候选里（`P_fix` 重归一化） | 否 |
| 总预算耗尽（`total_budget_ms`） | 立即落 L1，不再尝试 | 否 |
| 全部层级失败 | L1 本地技能（扫描/求注意/保持），一定成功 | 否 |
| 摔倒 / 桌沿 / 视觉彻底丢失 | 安全否决：不升级，本地处置 | 否 |

两个防抖机制（都是为了别让机器人变成复读机）：

- **触发驻留 `dwell_ms=150`**：判据要在门限之上连续停留 150ms 才真的升级。
  给离散检测量的一阶平滑留出收敛时间，也避免「刚过线就用第一版估计选层级」。
- **事件闩锁 + 重新武装**：一次升级结束后，同一件事（请求层级不升反降）不再重复问；
  只有当 `p_esc` 掉回 `rearm_p=0.3` 以下（事件确实过去了），或者**要的层级变高了**（问题变大），才重新武装。
  没有它，一个人一直指着杯子，机器人会每 0.6 秒问一次云端。

**为什么等待期不清零头部**：头是此刻唯一还在采集信息的通道，停下来就真的瞎了。
**为什么等待期清零车轮**：以 0.3m/s 等 2.5s 就是 0.75m 的盲走，这不可接受。

### 5.1 真实 L2：agent_bridge 接入（本机实测）

`local_agent.LocalAgentBackend` 把升级请求接到 `../agent_bridge/server.py` 上。
那个服务是独立可测的（`python server.py --selftest`），本仓库**不修改**它，只调用它的
`POST /agent/task` 和 `GET /agent/health`。两侧契约不同，中间只有这一层适配器：

```
esc/1 请求                      agent_bridge 协议
──────────────                 ─────────────────────────────────────────
why[0].k -> 风险族        ──▶   {"intent": "<自然语言>", "level": 2}
                                 （不指定 action：让 agent 自己的 planner 挑）
                                {"ok":1,"action":"disk","planner":"rule",
                                 "detail":"C: 24G free; D: 110G free","elapsed_ms":0.7}
                          ◀──   Instruction{level:2, intent:"pc_disk",
                                 prog:[emote(think,400),track], say:"磁盘 C: 24G free …",
                                 args:{detail, planner, agent_ms, roundtrip_ms}}
```

| 风险族 | 意图（命中规则 planner 的关键词） | 动作 | 真实副作用 |
|---|---|---|---|
| language | 「记下这次升级：机器人听到声音但没听懂。」（"记下"） | `note` | 向 `robot_notes.log` 追加一行 |
| unknown | 「报告 PC 的系统状态。」 | `system_status` | 真主机名 / 平台 / 磁盘 / 时间 |
| stakes | 「PC 上各磁盘还剩多少空间？」（"磁盘/空间"） | `disk` | 真剩余空间 |
| context | 「现在几点了？」（"几点"） | `clock` | 真时间 |
| planning | 「记下这次升级：机器人需要多步规划，本地做不了。」 | `note` | 同上 |
| blind | 「看看 PC 屏幕上现在是什么情况。」（"看看"） | `screenshot` | 写 `screen.png`（≈360ms，全表最慢） |

**为什么不让 backend 直接指定 `action`**：`action` 是 agent_bridge 的显式分支，直接填它就绕过了
planner，「PC agent 自己会挑动作」这件事就没被验证。传自然语言意图、由 agent 的 planner
（有 key 用 LLM，没 key 用规则）决定，才是在测真实链路。`action_hint` 只留给"调用方确知要哪个动作"
的场景（测试用它验证 `explicit` 分支）。

**运行**：`python demo_real.py` 自动拉起子进程（随机空闲端口）并跑三个真实场景；
服务已经在跑时用 `python demo_real.py --no-spawn --url http://127.0.0.1:8899`。
`detail` 是不是真的由 `detail_check.py` 用本机事实反算（hostname 对 `socket.gethostname()`、
磁盘对 `shutil.disk_usage`、时间对 `datetime.now()`、日志对最后一行的字符数与时间戳），
不看字符串长度、不信任 agent 的自述。

**延迟（本机 127.0.0.1，多轮实测区间）**

| 环节 | 实测 | 说明 |
|---|---|---|
| agent 内部执行 | 0.4~1.0ms（clock/disk/note）；27~33ms（system_status） | `shutil.disk_usage("C:\\")` 在 Windows 上不便宜 |
| HTTP 往返（客户端） | p50 1.2~16ms，p95 5~30ms | 随主机负载波动，同一台机器不同时段差 10 倍 |
| hub 观测（50Hz 环） | +0~20ms | 20ms 一拍，回包落在两拍之间就等下一拍 |
| 升级链总耗时（判据超线→第一条指令） | 183~207ms | 其中 150ms 是 `dwell_ms`，L2 本身只占 20~42ms |
| 超时回退（ttl=300 / 900） | 280~302ms / 821~831ms | = 0.9×ttl（socket 超时）+ 一拍 |
| 掉线回退（进程被杀） | 155~164ms | 建连超时，**不**随 ttl 增长 |

**三处必须写下来的工程约束**（都是实测踩出来的）：

1. **`available()` 不能做网络 IO**。hub 在 `decide()` 里每拍问一次（50Hz），
   在这里发 HTTP 就等于把 L0 拖进网络路径。实现是后台线程每 `health_ttl_s` 探一次、
   `available()` 只读缓存布尔。
2. **单次探测失败不能把 L2 踢出候选**。实测主机冷启动/杀毒扫描会让本地探测偶发
   250ms 超时；早期版本一次失败就 `available()=False`，于是指物场景悄悄从 L2 掉到 L1——
   判据和日志都自洽，只是根本没走 PC。现在要连续 `fail_threshold=2` 次失败才下线，
   一次成功立即恢复；探测还带单调闸门，更早开始、更晚返回的旧结果不许覆盖新结果。
3. **建连超时和等回包超时必须分开**。实测：服务进程被 `TerminateProcess` 杀掉后，
   Windows 不对该端口的 SYN 回 RST，而是静默丢弃，连接会挂到客户端超时为止。
   用单一超时就会把"进程死了"误判成"agent 卡住"，TTL=900ms 时要等 810ms 才回退。
   现在建连单独限 150ms，掉线回退从 810ms 降到 160ms；只有"连上了但没回包"才走满预算。

**失败模式**（全部走 §5 已有的降级路径，没有任何异常穿透到控制循环）：

| 失败 | 映射 | 实测行为 |
|---|---|---|
| agent 没启动 | `available()=False` | 同拍落 L1；L2 零调用、零失败、零崩溃 |
| 进程中途被杀 | `BackendUnavailable` | 160ms 后回退 L1；此后 `available()=False`，后续升级不再试 L2 |
| 任务端点卡住 | `BackendTimeout` | 0.9×ttl 后回退 L1（300ms→293ms，900ms→823ms） |
| 404 / 500 | `BackendError` | 降级；**不**把这一级判成不可达（应用错误 ≠ 不可达） |
| 200 但不是 JSON | `BackendError` | 同上 |
| `ok=0`（动作自己失败） | `BackendError` | 同上；detail 原文进错误信息 |

超时场景**不修改** `server.py`：`slow_bridge.py` 按文件路径加载它，只覆盖 `do_POST`
注入 `--delay-ms` 的延迟（健康检查不打延迟），`--delay-ms 0` 等于原行为。

**没证明的**：没有 `DEEPSEEK_API_KEY`，所以走的是规则 planner，「LLM 会挑对动作」仍未验证
（与 §8 第 3 条是同一个缺口）；`screenshot` 依赖桌面会话、单次 ≈360ms，没有进测试矩阵。

## 6. 闭环：上层指令怎么落回 CfC 的动作空间

上层的输出**不是**自由文本，而是一个结构化的**动作程序**（`prog`）：

```json
{"id": 3, "level": 2, "intent": "look_at_target", "ttl_ms": 1500,
 "prog": [{"op":"head","deg":40.0,"ms":300},{"op":"hold","ms":250}],
 "say": null, "confidence": 0.66}
```

原语就是 CfC 的输出通道：`head(deg±45) / yaw(dps±90) / vx(mps±0.3) / emote(id0-7) / hold / stop / track / say`。
所以**上层指令天然落在 CfC 的动作空间里，不需要第二套动作定义**：

```
Instruction  ──SkillExecutor（本地，50Hz）──►  CtrlAction(head_des, vyaw_des, vx_des, mode, emote)
                                                      │
                                        （与 CfC 输出同构，进同一个仲裁器）
```

三个细节：

1. **`yaw` 原语自动做头部反向补偿**（机身转多少、头反向补多少），这是 §7.3「保持注视」的同一件事，
   否则「转过去看看」会把视线甩开。
2. **程序在本地播放，不在网络播放**。指令一次性下发，之后即使 WiFi 断了也能把这段动作做完——
   这是「一次成型」原则在决策层的一次复用。
3. **`track` 原语 = 立刻交还控制权**，用于「看完了，你继续」。

**已知缺陷（必须写出来）：干预回声问题。**
上层接管期间，CfC 的隐状态并不知道自己被架空了。程序结束时，CfC 会接着输出它接管前的计划，
和上层刚做的事打架（例如「转过去看看」刚转完，CfC 立刻把头拧回来）。
正确的做法是给观测加一维「我刚被接管过」的 token（`obs[106] = 1.0` 持续 N 帧），让网络学会这件事。
这需要重训模型并升 blob 版本，本阶段**没有做**，只在 `FIRMWARE_CHANGES.md §5` 里留了位置。
当前的缓解是仲裁器本来就有的头部低通（`head_lpf`）和 3 秒 `stable_yaw` 冻结窗口，
动作上不会抖，但「意图」层面确实会打架。

## 7. 机器人侧要跑什么（成本）

| 计算 | 放哪 | 成本 |
|---|---|---|
| 12 个势函数 | `cfc_task`，每 20ms | 12 段 smoothstep ≈ 60 次乘加 |

## 8. 验收：测试证明了什么，没证明什么

`python test_hub.py` → **90/90 PASS，约 9 秒**。覆盖：

- **路由正确性**：12 个场景（跟踪 / 挥手 / 看不清 / 丢失 / 指物 / 说话多步 / 查资料 / OOD / 特征出域 / 没把握靠近 / 语义过期 / 满血反证）+ 3 个安全否决 + 层级不可用过滤 + `P_fix` 重归一化。
- **超时与降级**：L3 超时 → L2（尝试链 `[3,2]`）；云端 down → 直接 L2；全挂 → L1；后端返回非法指令 → 拒绝并降级；迟到回复 → 丢弃并计数。
- **不变量**：等待期每拍都有合法指令、车轮清零、头仍在跟人；动作永远在 ±45°/±90°/±0.30 内；`track` 立即交还。
- **非法输入**：600 组脏观测（NaN/Inf/None/字符串/1e12/负时间/错类型）零异常、零越界；`tick(None)` 不崩；14 类非法指令全部被拒。
- **延迟统计**：每级计数 + 分位数；超时也算一个延迟样本。
- **可训练性**：注入 3 个已知权重能从 2500 条样本里学回来（无关权重被压到约 0.2）；路由头 92.8% 准确率。

`python test_real_backend.py` → **58/58 PASS，约 11 秒**（另起进程，真的拉起 `agent_bridge` 子进程）。覆盖：

- **接得上**：4 个真实动作（`note`/`system_status`/`disk`/`clock`）逐个执行，detail 用本机事实反算核对；
  `action_hint` 的 explicit 分支、`parse_instruction` 校验、`esc_id` 回传都对得上。
- **端到端**：真实配置（dwell=150ms / EMA）下判定升级 → 真的写一行日志 → 结构化指令回到 L0 播放；
  对照组（L2 不可用）证明这行日志确实来自 L2。
- **对照实验**：正常 15 次（全部 L2、PASS）、agent 未启动 10 次（同拍落 L1、L2 零调用）、
  agent 超时 10 次@ttl300 + 3 次@ttl900（0.9×ttl 内回退）、运行期被杀（160ms 回退）。
- **失败模式**：404、200+非 JSON、进程被杀，全部映射成 `BackendError` / `BackendUnavailable`，零崩溃。

**没证明的**（诚实清单）：

1. 权重是**先验**，没在真实数据上训练过。行为正确性来自 §3.4 的手算，不是统计证据。
2. 没有真机、没有真 WiFi，也没有真 YOLO 特征；延迟表里 L0 和 **L2（真实 HTTP）** 是本机实测，
   L2 的 mock 行与 L3 仍是建模值。
3. mock 后端和规则 planner 都能证明链路、超时、校验、降级是活的，**不能**证明真 LLM 会给出好指令
   （§5.1 的规则 planner 也一样）。
4. `p_esc` 未经校准，所以 §3.4 的阈值推导目前在「权重先验」这一层自洽，还没到「概率可解释」那一层。

## 9. 这个架构最脆弱的地方

**`P_fix` 的先验矩阵是拍出来的，而它同时决定「去哪一层」和「愿不愿意花那个代价」。**
门控的权重错一点只是早问晚问；但 `P_fix` 错一点，机器人就会持续地、自信地找错人
（把该看画面的问题丢给云端，把该问语言的活留给本地扫描），
而且这种错误在日志里看起来很「合理」——因为每一步的贡献分解都自洽。
唯一可靠的解法是拿到 §3.7 第 1 类事后标签，把 `W_Lk` 也训出来，并把触发分布当作运维指标盯着。

次要但真实的风险：`action_conf` 这个输入目前来自 CfC 的 mode softmax，而分层 softmax 的 top-1
概率系统性偏高。它直接乘进 `s_irrev` / `s_approach` 两个 stakes 势函数，
**如果它没有校准过，这两项就等于被常数缩放，权重先验会整体偏小**。上线前必须做温度标定。

真实 L2 接上之后还多了一条：**校验层只保证「指令合法」，不保证「指令有用」**。
`agent_bridge` 目前只有 5 个白名单动作、没有视觉，所以「指着杯子」这个升级会被翻译成
「记一笔日志」——动作合法、detail 真实、全链路绿灯，但对用户的问题没有帮助。
这正是 §5.1 的映射表应该被读成「链路已经通了」而不是「机器人变聪明了」的原因。
补法有两条：给 L2 真的视觉（取帧 + 物体识别），或者在 L2 侧加一个
「这次执行是否回答了升级理由」的判据，让语义不相关的指令被降级而不是被接受。
